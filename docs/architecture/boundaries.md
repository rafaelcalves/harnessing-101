# Core boundaries and adapter contracts

Status: **Proposed, Phase 0; no implementation**. Stack proposal: [ADR 0001](../adr/0001-language-and-runtime.md).

**INFERENCE — scope.** Every contract below is a proposed requirement, not a claim about running software. The core owns agent/task/message state, transition rules, execution policy, and recovery decisions. Adapters translate requests or perform effects. A host wires them together. There are **ten ports: four inbound and six outbound**. No UI framework, command parser, operating-system process object, filesystem watcher, or network client is a core dependency.

## Common vocabulary and compatibility

**INFERENCE — terminology.** A **hive** is the team of agents organising itself; a **workspace** is the on-disk directory the tool owns and writes. Version 1 stores one hive in one workspace. Workspace IDs identify the storage/command scope, not an agent collective; no multi-hive mapping is implied.

**INFERENCE.** Public records use opaque string IDs; bounded strings; integer counters; UTC timestamps for display/audit; tagged result/error records; and immutable snapshots. Commands contain a workspace ID, request ID, command kind, payload, and optional expected revision. No arbitrary executable callbacks or language-runtime objects cross the public boundary. Byte output is represented as bytes in-process and base64 in a future JSON transport. Schema version is explicit in persisted and transported envelopes.

**INFERENCE.** The initial contract version is 1. Unknown command kinds and incompatible major versions fail explicitly. Readers may ignore additive optional fields; new required fields or changed meanings require a major revision. Errors have stable codes: InvalidArgument, NotFound, Conflict, Denied, Unsupported, Busy, IOFailure, CursorExpired, and RecoveryRequired. Human-readable details are supplementary. A transport maps these into CLI exit status or GUI feedback; neither representation is a domain error.

## Inbound ports — what any UI can use

| # | Port | Operations and required semantics |
| --- | --- | --- |
| 1 | Commands | Execute a versioned command and return a receipt containing request ID, committed revision, and operation ID when work continues asynchronously. Domain commands include RegisterAgent, UpdateAgent, CreateTask, TransitionTask, ReportTaskResult, AcceptTaskResult, RejectTaskResult, SendMessage, AcknowledgeMessage, StartRun, StopRun, and SetRunBudget. |
| 2 | Queries | GetSnapshot(workspace), GetAgent(id), GetTask(id), GetMessage(id), GetRun(id), GetOperation(id), and GetCapabilities(workspace). Snapshot includes a consistent workspace revision, event cursor, and collections. Capabilities explicitly identify unavailable operations/platform functions. |
| 3 | StateEvents | Subscribe(workspace, afterCursor, cancellation) yields ordered committed events and a cursor. Each event includes ID, kind, schema version, workspace revision, timestamp, subject IDs, and a typed payload describing a state transition. |
| 4 | RunOutput | ReadOutput(runID, afterOffset, byteLimit) and FollowOutput(runID, afterOffset, cancellation) return persisted chunks with next offset, stdout/stderr identity, bytes, and capture timestamp; terminal status distinguishes complete capture from interrupted capture. |

**INFERENCE — version 1 command payloads.** RegisterAgent takes `agentID`, `displayName`, and optional `profileID`; UpdateAgent takes `agentID` and an explicit patch of those mutable fields. CreateTask takes `taskID`, `title`, and optional `assigneeID`, initially Todo. TransitionTask takes `taskID`, `fromStatus`, `toStatus`, and a reason for Blocked or reopening; states are Todo, Doing, Blocked, AwaitingReview, and Done. This generic command permits only Todo→Doing, Doing→Blocked, Blocked→Doing, and authorized human Done→Todo reopening. Reporting, acceptance, and rejection use the dedicated commands below; generic transitions into AwaitingReview or Done fail InvalidArgument. SetRunBudget takes `runID`, optional elapsed-time limit, and optional reported-token limit; limits must be positive and unsupported token reporting fails Unsupported. StartRun takes `runID`, `agentID`, and configured `profileID`; StopRun takes `runID` and a reason. SendMessage takes `messageID`, `senderAgentID`, `recipientAgentID`, `kind`, UTF-8 `body`, and optional `taskID` and `replyToMessageID`; kinds are Request, Inform, and Result, with no implied automatic reply. Unknown IDs fail NotFound. These are proposed minimal semantics, not copied file conventions.

**INFERENCE — completion and acceptance contract.** ReportTaskResult takes `taskID`, a new `resultID`, required `expectedTaskRevision`, a nonempty summary, and one or more workspace-relative local artifact references. Only the current assignee, identified by the host-supplied caller scope, may report from Doing. The core records an immutable result with reporter and timestamp, sets the current result ID, and transitions Doing→AwaitingReview atomically. A report records claimed evidence; it does not establish artifact existence, correctness, or acceptance. The task stays AwaitingReview until a decision is recorded, including across restart.

**INFERENCE.** AcceptTaskResult takes `taskID`, `resultID`, required `expectedTaskRevision`, and an optional review note. RejectTaskResult takes the same identifiers and revision plus a required reason. Both require a host-authorized **human reviewer**, the task in AwaitingReview, and the exact current result ID. Acceptance atomically records reviewer, timestamp, result ID, and decision, then changes AwaitingReview→Done. Rejection records the same audit fields and reason, then changes AwaitingReview→Doing for rework. Result history is retained; rework requires a new result ID. Reopening Done preserves past acceptance but clears the current result selection. A stale task revision, superseded result, or concurrent decision fails Conflict; an unauthorized actor fails Denied. Task revision is distinct from the workspace revision and is returned by GetTask and snapshots. Command idempotency still applies, so replaying an accepted request returns its original receipt.

**INFERENCE — authority and UI cost.** Human review authority comes from host policy, never a `reviewerID` or `isHuman` field supplied by an agent. The core requires this capability even when invoked through a non-CLI adapter; agent scopes cannot accept or reject results. Actor identities and timestamps accompany all task status updates in queries and events. A UI adds one status, a result summary/artifact view, and separate Accept/Reject actions targeting the displayed result and task revision. It must label AwaitingReview as “reported complete; awaiting acceptance” and reserve Done for accepted work. The authorized human may also be the assignee; version 1 does not invent a second-person review requirement. This enforces application-level authority, not protection against arbitrary same-user filesystem tampering; identity isolation remains a security-design responsibility.

**INFERENCE — acknowledgement command.** AcknowledgeMessage takes `messageID`. It means the addressed recipient explicitly reports receiving the message; it proves neither comprehension nor work completion. Only a caller scoped to that recipient may acknowledge it. The core records `acknowledgedBy`, host timestamp `acknowledgedAt`, and the acknowledgement event atomically. A repeated acknowledgement of the same message by that recipient is a successful no-op even with a new request ID; it preserves the first timestamp and emits no duplicate event. Unknown messages fail NotFound and wrong-recipient callers fail Denied. UIs display acknowledgement as its own fact with recipient and timestamp; pending-message views filter on missing acknowledgement rather than missing publication. Sender, publisher, filesystem scanner, and UI viewer must not acknowledge on the recipient's behalf merely because they accessed a file. An explicit acknowledgement can also arrive through the validated file-protocol control record described below.

**INFERENCE — event and mailbox records.** Each successful domain mutation emits its corresponding named event: AgentRegistered, AgentUpdated, TaskCreated, TaskTransitioned, TaskResultReported/Accepted/Rejected, MessageQueued/Published/Processed/Acknowledged, RunStarting/Started/Stopping/Exited/RecoveryRequired, RunBudgetChanged, or OperationCompleted. Payloads identify changed fields and their resulting values; they exclude secrets and raw output. Task result/decision events include task revision, status, result ID, and reporter/reviewer identity and timestamp, allowing a consumer to apply the whole change once. Dedicated report/decision commands emit their dedicated event rather than an additional generic TaskTransitioned event for the same change. A mailbox envelope carries version, workspace ID, message ID, sender/recipient IDs, kind, body, creation time, optional task ID, and optional reply-to ID. File adapters impose configured size bounds and validate the full envelope before presenting it to the core. Agent IDs in an envelope are routing claims, not authenticated identities; host policy supplies the caller's allowed command scope independently of UI-provided fields. Profile approval/configuration is host-supplied policy in version 1, not arbitrary shell text accepted by StartRun.

**INFERENCE — command completion.** Successful Execute means validation passed and intent/state was durably committed, not that a child finished or a message was read. Commands that fail validation commit nothing. StartRun/StopRun return operation IDs, with progress and terminal outcomes obtained through Queries/StateEvents. Operation states are Pending, Running, Succeeded, Failed, or RecoveryRequired. Run states are separately Starting, Running, Stopping, Exited, or RecoveryRequired; spawn failure is Exited with a spawn-failure outcome. Unsupported Phase 3 operations return Unsupported in Phase 2.

**INFERENCE — retries and conflicts.** Repeating a request ID with the same payload returns its recorded receipt; a different payload returns Conflict. Request IDs are scoped to the host-established caller identity; authorization is checked before receipt replay. The store retains receipts until workspace reset in the initial design. An expected-revision mismatch returns Conflict before mutation. A client disconnect does not undo an accepted command. Cancelling a subscription only detaches that subscriber; stopping a run requires StopRun. A lost receipt is resolved by retrying its request ID, not issuing a new StartRun.

**INFERENCE — gap-free observation.** Read a snapshot at revision R and subscribe after its associated cursor. Events committed meanwhile remain replayable. At the adapter boundary delivery is at least once: consumers deduplicate event IDs and apply revisions monotonically. An expired cursor returns CursorExpired and the earliest available cursor; clients reload a snapshot. Never silently skip retained events. Slow subscribers use bounded queues and receive a resumable disconnect, never block a state commit or grow memory without limit. Events describe committed facts; the CLI cannot treat a progress spinner as state.

**INFERENCE — output is separate.** A per-run journal assigns monotonic byte offsets across both channels in capture order; this does not claim causal ordering between stdout and stderr. UTF-8 characters may span chunks. Output is not copied into state events. A slow reader resumes from disk. Retention loss returns CursorExpired with the earliest offset. Journal size limits are configured explicitly; on capture write failure the core stops the run and records failure where possible, rather than continuing with silently missing output. Successful run exit and successful output capture are separate outcomes. Consumers must treat terminal control sequences as untrusted output.

## Outbound ports — what the core requires

| # | Port | Adapter contract |
| --- | --- | --- |
| 5 | StateStore | Load a consistent snapshot and journal tail; Commit(expectedRevision, changes, events, receipt, pendingEffects) atomically; Replay(afterCursor, limit). A failed/conflicting commit publishes no events. Successful return means durable data under the documented local-filesystem guarantee. |
| 6 | Mailbox | ScanInbox(agentID, cursor), Publish(messageID, envelope), and Archive(messageID). Publish is idempotent by message ID; readers only see complete envelopes. Scan can repeat entries. Invalid envelopes yield typed validation failures and remain available for diagnosis. |
| 7 | ProcessSupervisor | Capabilities; Start(runID, executionSpec); Observe(runID); Stop(runID, graceDuration); Recover(runID). Produces started, output, and exit observations tagged by run ID. Guarantees at most one concurrent spawn per run ID within a controller lifetime. Exposes capability failures rather than pretending every platform has equivalent termination. |
| 8 | OutputJournal | Append(runID, channel, bytes, captureTime), ReadAfter(runID, offset, limit), Follow(runID, offset), and Finish(runID, captureOutcome). Append assigns the offset only after persistence; readers see complete chunks. Enforces the configured storage limit and reports retention/write failures. |
| 9 | Clock | WallNow for audit timestamps and monotonic elapsed-time/deadline operations for live supervision. Tests supply controlled time. Persisted wall times never substitute for a continuous monotonic clock across restart. |
| 10 | IDSource | NewID returns a workspace-unique opaque ID; tests supply deterministic IDs. IDs contain no required path, PID, display-name, or timestamp encoding. Collision at persistence is a conflict, not overwrite. |

**INFERENCE — files and commit boundary.** File persistence remains human-inspectable: versioned records/journals and complete message envelopes. It is not direct UI access to live files. One host holds an exclusive operating-system-backed workspace lock; a second writer fails Busy. Do not steal a lock based on elapsed wall time. Atomic commit can be implemented with a committed journal record and derived snapshots; it must not pretend several independent file renames form a transaction. A torn trailing record is detected during recovery. Existing committed records must survive the documented crash model. Unverified network filesystems are unsupported rather than assumed equivalent to local disks.

**INFERENCE — mailbox effects.** Commit outgoing message intent with its stable ID before Publish; retry publication after a crash, then record completion. On receive, commit the message ID and ingestion facts before scheduling any effects; archival follows the explicit acknowledgement rules below. Duplicate scans are harmless through persisted deduplication. Mailbox I/O and the state store do not share a transaction. Message delivery facts distinguish queued (outgoing intent committed), published (complete recipient envelope made available), processed (controller ingested the envelope), and acknowledged (explicit recipient acknowledgement committed). These are separately recorded facts with timestamps, not one scalar status: controller ingestion is not recipient acknowledgement or work completion. GetMessage and snapshots expose all four facts plus acknowledgedBy/acknowledgedAt; absent acknowledgement is labelled “not acknowledged,” never inferred from another fact. Acknowledgement may arrive before the controller records Publish completion; preserve it without fabricating a publication timestamp or later downgrading it. A task result or acceptance is a separate record, not a message delivery state. External agents may write complete inbox envelopes through the documented protocol; filesystem notifications are hints followed by a scan, never authoritative delivery evidence.

**INFERENCE — file acknowledgement and archival.** The Mailbox adapter accepts a second envelope type, MessageAcknowledgement, carrying schema version, workspace ID, unique control-record ID, original message ID, and recipient agent ID. This is a protocol control record, not a Request/Inform/Result message and never requests an acknowledgement itself. The adapter supplies the host-validated submitting agent scope separately from the claimed recipient field; if a file ingress cannot establish that scope, reject/quarantine the record rather than grant recipient authority. Ingestion applies the same core checks as AcknowledgeMessage, deduplicates the control-record ID, commits the acknowledgement and event, and only then archives that control record. For a recipient's work message, ingestion alone does not remove it from the pending inbox: Archive is scheduled only after an explicit acknowledgement is durable. The message body/history remains queryable after archival. Failure to archive is retried idempotently and cannot erase acknowledgement. The control record may arrive through the same existing Mailbox port; no additional port is needed.

**INFERENCE — supervision and recovery.** An execution spec references an approved local executable profile and supplies argument elements, a validated working directory, approved environment references, I/O mode, and termination policy. Resolve paths, environment secrets, file descriptors, signals, process groups, and platform job objects inside the adapter. Do not spawn through a shell by default. The core sets policy and consumes normalized observations; it does not inspect process IDs. Interactive terminal support is an explicit capability, not an accidental consequence of a caller having a terminal.

**INFERENCE.** Persist StartRun intent before invoking Start. After a controller crash, Recover must establish process identity/ownership or return Unknown; a reused PID is insufficient. The core then marks RecoveryRequired and refuses an automatic duplicate spawn. Exactly-once process creation across a crash is not promised. Stop means graceful termination followed by configured forced termination of the owned process tree where supported; completion requires observed exit. A kill request alone is not an Exited event. Output gaps after a host crash are reported, not fabricated. Resource/token usage unsupported by an agent remains unknown rather than counted as zero.

## Hosting, locality, and what must not leak

**INFERENCE.** The host owns workspace locking, adapter construction, signal handling, and controller lifetime. Closing one UI does not stop runs managed by a continuing host. Explicit host shutdown requests termination and waits or reports failure; unexpected death invokes recovery on the next start. Durable background hosting is Phase 3 work, not an implicit Phase 2 daemon. Other UIs connect through a future local adapter to the same owner, never open a competing store writer. No default TCP listener is required: standard-input/output pipes suffice for a future out-of-process GUI bridge. Local transport permissions and framing belong to that adapter.

**INFERENCE — must not leak.** Keep these outside the core: CLI flags, exit codes, prompts, ANSI rendering, terminal size, GUI widget/state objects, HTTP concepts, transport connections, framework exceptions, absolute storage layout, watcher notifications, raw operating-system handles, platform signal names, provider SDKs, secret values, and implicit network operations. Keep budget decisions, command authorization, allowed transitions, retry/deduplication rules, and shutdown policy inside the core. An adapter may translate a user's answer, but must not decide a domain policy while displaying it. Treating an interface change as permission to change command semantics violates this boundary.

**INFERENCE — hardest boundary.** Interactive process control is the hardest leak to prevent: terminal attachment, cancellation, UI disconnect, and run termination look related but have different owners. A GUI closing a window and a CLI losing its terminal must yield the same domain outcome for the same explicit command. Runtime locality is an application obligation, not proof that arbitrary child programs cannot access the network. Agent profile egress intent must be visible and explicitly authorized before starting that profile; enforcement beyond application policy requires a separate security design.

## Phase 2 replacement proof and open decisions

**INFERENCE — acceptance scenario.** Drive the same core first from the CLI, then from a throwaway scripted adapter with no CLI imports. Both register agents, create/transition a task, send a message, and observe identical normalized state/events using deterministic IDs/time. Show publication and ingestion without acknowledgement; explicitly acknowledge as the recipient and verify it survives restart. Report a result and verify AwaitingReview survives restart without becoming Done; reject it as an authorized human, submit a new result, and accept that exact result. Assert wrong-recipient acknowledgement and agent acceptance return Denied, direct Doing→Done is rejected, stale-result acceptance returns Conflict, and duplicate acknowledgements/decision requests create no duplicate facts. Exercise both command and file-control acknowledgement through the same core checks. Replay after disconnect and submit a duplicate request; prove no duplicate transition or message. Use a fake ProcessSupervisor and seeded OutputJournal to exercise output replay, a slow subscriber, cancellation, and cursor expiry without implementing Phase 3 supervision. Verify both adapters receive Unsupported for unavailable real process control. Assert the core imports neither adapter and requires no changes when the scripted adapter is added. This is a proposed test, not a passed one.

**UNKNOWN.** Approved platforms, terminal requirements, exact retention/storage limits, crash-durability guarantees, schema migration procedure, and host recovery capabilities still need owner/security/quality review before implementation of their respective phases. Ports expose these uncertainties explicitly; they are not reasons to silently return success or broaden the product scope.

## H101-7 — semantic corrections (2026-09-19)

**SECONDARY SOURCE.** [Product definition §2](../product/definition.md) distinguishes reported completion from human acceptance and acknowledgement from completed work. [Quality audit findings 4–5](../quality/definition-of-done.md) identified that the earlier contracts did not express those distinctions. The orchestrator's H101-7 terminology ruling distinguishes the hive (agent team) from its workspace (owned directory).

**INFERENCE — change and rationale.** Added AwaitingReview and ReportTaskResult/AcceptTaskResult/RejectTaskResult so a reported result cannot silently become accepted work. Dedicated decisions carry reviewer authority and a result/revision binding; a reviewer field alone would leave transition authority ambiguous. Added AcknowledgeMessage, MessageAcknowledged, a file acknowledgement control record, and queryable acknowledgement facts so publication, ingestion, archival, or a task result cannot masquerade as recipient acknowledgement. Rejection/rework and replay behavior are explicit. Ten ports remain unchanged; only their vocabulary and semantics expand. This repairs the still-unimplemented version 1 design, not a migration of shipped data. No pushback on either product rule; neither rule alone proves human review quality or agent understanding.

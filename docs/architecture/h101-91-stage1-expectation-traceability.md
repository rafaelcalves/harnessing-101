## Named ambiguities

1. **Generated entity IDs:** boundaries:53 specifies workspace-unique opaque IDs and deterministic test IDs; ADR 0003:43 requires generated IDs to be surfaced for recovery. Neither defines which omitted entity IDs must be generated, their display representation, or how independently generated entity IDs are compared across runs. ADR 0003:60 permits normalization only for generated **event** IDs, not entity IDs. Stage one's explicit `t1`, `m1`, `res1`, `res2` values avoid this gap; they do not settle it.
2. **IOFailure:** ADR 0003:42 clearly requires error preservation, request identity, and honest uncertainty. It does not specify a deterministic fault-injection mechanism. Furthermore, the two requested source documents have not reconciled the later taxonomy: ADR 0004:19–31 specifies OutcomeUncertain for uncertain mutation outcomes and reserves ordinary IOFailure for other failures; :55 states the conservative rule during migration. Thus “post-application failure must literally be IOFailure” cannot be justified from the older row alone. There is a document reconciliation gap and no IOFailure expectation in `spec.go`, not evidence that the author chose an unsupported error literal for this path.
3. **Mailbox revisions:** boundaries:34,57 requires separate delivery facts/events and durable recording, not a fixed total workspace revision after SendMessage or a fixed scheduling order for publication/ingestion. No such total appears in `spec.go`. Its :28–29 blanket claim that **each successful command** increments revision by one from zero has no source in these documents and is too broad: original-receipt replay and acknowledgement no-ops are explicit exceptions (boundaries:32,38). Exact initialization, increments for new commits/no-ops, and mailbox integration scheduling need a stated contract before literal arithmetic is certified. Task revision is explicitly distinct (boundaries:28), but its initial numeric value and increment are likewise unstated; the scenario consumers' numeric task-revision preconditions cannot be sourced from that distinction alone.

No specification, tests, or adapter code changed to close these gaps. This ruling certifies the sources identified above, not complete UI-01..04 coverage or suite execution. UI-05..08 remains outside this stage.

## Addendum — explicit A1/A2/A3 rulings after `5c4f6e7`

Read `internal/adaptercontract/AMBIGUITIES.md` alongside `expected/spec.go`. The added three-line package comment shifts the earlier spec.go references by three lines; the original review references above remain pinned to its first stage. The per-item traceability verdict remains unchanged.

**A1 / UI-03 — conditional generation obligation.** UI-03 does not require an adapter to generate entity IDs when its command contract requires the caller to supply them. For such a scenario, preserving the supplied request ID and replaying its original receipt is the specified retry identity behavior (ADR 0003:43; boundaries:19,38). Workspace revision is an observation token, not a replacement for the request ID. No extra success echo of every caller-supplied entity ID is mandated by that sentence. If an adapter does allocate an ID needed for recovery, it must expose that ID through its documented response/recovery interface; a generated request ID must be recoverable without already knowing that ID. Exact output formatting is adapter-specific (ADR 0003:60,72). A successful-response echo alone does not prove recovery when that response is lost. Stage one's explicit-ID fixtures are justified; they do not establish generated-ID recovery. Which IDs may be omitted/generated, the interrupted-response recovery mechanism, and cross-run entity-ID normalization remain document gaps. The CLI behavior described in A1 is an implementation report, not the source of this ruling.

**A2 / UI-02 — partial coverage is not a waiver.** Denied/Conflict expectations are traceable, but they cannot discharge the separately specified uncertainty behavior (ADR 0003:42). Deferring that scenario is staging, not a conclusion that UI-02 is fully demonstrated. For uncertain mutation outcomes, use ADR 0004:19–31's stable code and structured effect/confirmation/request identity; its :27 expressly excludes diagnostic wording as a conformance assertion. Do not revive the older suggested fsync-detail substring assertion. Ordinary IOFailure must remain an error; an unclassified mutation IOFailure remains conservatively unconfirmed under ADR 0004:55. Read/query failures also must not become success or a complete-looking partial view (ADR 0003:29); a read error does not itself imply a new mutation occurred. A deterministic injected-failure fixture may be chosen by QA without copying adapter wording, but must identify which effect boundary it simulates. The specification does not mandate the injection mechanism or stage deadline. ADR 0003/boundaries still need explicit reconciliation with ADR 0004; this addendum records the source hierarchy rather than silently changing their text.

**A3 / UI-04 — revision is observable domain state, including mailbox mutations.** Yes: ADR 0003:27,29,60 explicitly includes snapshot revision, receipt revision, and event revisions among canonical observations. Boundaries:19–21,34,57 places durable delivery facts in that same workspace state. A new committed publication or ingestion fact must advance the workspace's state version; it cannot alter the snapshot while leaving the version identifying that committed cut unchanged. The actor need not be a user. The number identifies a committed workspace state, not a count of user actions, completed tasks, or acknowledgements.

Compare exact revisions when the scenarios start from the same revision and execute the same defined commit sequence through the same observation point. Compare each command receipt to its own commit, not to a later snapshot after mailbox work. An extra mailbox commit between those observations legitimately changes the snapshot revision without changing the earlier receipt. Asynchronous runs at different delivery stages are different cuts, not evidence that revisions can be discarded or normalized away. Establish completion of the specified delivery facts before comparing a final cycle cut.

The reported `14 = 12 + 2` is consistent with twelve state-changing user commits plus two distinct mailbox-fact commits **if** the revision scheme starts at zero and increments once per such commit. Those numeric rules, commit grouping, and the final observation barrier are not established by the cited documents; neither this report nor a running adapter supplies an independent specification for them. A3's attribution of “each successful user command advances ... by one” to boundaries is therefore unsupported. Omission of a guessed total was justified during this review, but cannot become a permanent exemption from revision assertions. Record the revision arithmetic and deterministic scenario cut explicitly before certifying `14` (or another total) as the expected literal. This is a named specification follow-up, not a finding that mailbox wiring should stop advancing revision.

No adapter behavior, observed total, or successful test run was used to fill these source gaps. No tests, adapter code, ADR 0003, or boundaries text changed in this addendum.

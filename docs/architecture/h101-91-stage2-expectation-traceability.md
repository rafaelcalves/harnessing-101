## Expectations the architecture did not grant

**G1 — rendering is not canonical state.** `assert_test.go:153–178` requires `Queued:`, `Published:`, `Processed:`, `Acknowledged: (absent)`, `Recorded by:` and `unverified`; UI-05 also requires `claimed`. The meanings are specified, the exact capitalization/punctuation/placement are not. `cli_driver_test.go:99` checks the specified disclosure text specifically on stderr, whereas ADR 0002 requires visibility without naming a stream. The forbidden fragments in `driver_helpers_test.go:74–82` (`verified sender`, `validated`, `identity confirmed`, `✓`) are reasonable examples of validation cues, but a blanket substring prohibition anywhere in output is not specified: quoted untrusted body text or a negated explanation is not necessarily a validation badge. These may be CLI-local regression choices under ADR3:60, not universal cross-adapter requirements.

**G2 — event shape/cardinality.** `ui06_test.go:82` expects precisely `[ui06-t2]`. B:21,38 specifies subjects and resulting facts, not the exact SubjectIDs list for TaskCreated or its ordering. The concurrency helper similarly counts only singleton subjects. No specification forbids an additional relevant subject.

**G3 — cursor encoding/lifetime.** `ui07_test.go:61` and `harness_test.go:68` use literal `"0"` as a subscription cursor. Workspace revision 0 does not imply that cursor encoding; ADR3:80 explicitly allows epochs or validated replay floors. `ui06_test.go:109`/`harness_test.go:53–61` require restart expiry unconditionally, while ADR3:80 only requires it when retained history is unavailable. A replay-capable implementation is not forbidden. These are implementation-profile assumptions, not shared requirements. The nonempty-string check likewise has no explicit encoding source.

**G4 — strict raw delivery growth.** `harness_test.go:94–97` rejects equal revisions before deduplication. B:48 permits repeat delivery, and ADR3:80/B:103 allow several events at one revision. Strict growth is valid for deduplicated, one-event-per-group observations, but neither exact one-event cardinality nor duplicate-free raw delivery is established for this helper by the shared documents.

**G5 — unregistered assignee success.** The observation/restart cases in UI-06 and detach case in UI-07 start fresh, bind `engineer`, and create assigned tasks without RegisterAgent. `newEnv` only creates a directory/configuration; the assembly harness opens/binds sessions and seeds no agents. No specification says binding a principal registers an agent. B:24 says unknown IDs fail NotFound. These success expectations have no architectural basis and appear contrary to that general rule; binding authority is not registry existence. This is a fixture/specification conflict to resolve, not a new authority exception granted by this review.

**G6 — detail and validation precedence.** `ui08_test.go:41` requires nonempty error detail. B:13 describes details as supplementary, not mandatory. Its sample StartRun lacks agent/profile fields, StopRun lacks reason, and budget uses a frontend-specific shape. The documents do not settle Unsupported versus InvalidArgument precedence for malformed requests to unavailable operations. Unsupported availability semantics are traceable; this precise precedence is not.

**G7 — task revision arithmetic.** B:30 distinguishes task and workspace revisions; B:103 defines only the latter. Crossover's 4/5/6/7 task revision inputs still assume an initial value/increment not explicitly defined. This is the stage-one gap, not a new defect created by stage two.

**Test controls, not domain requirements.** Three-/five-second waits and twenty concurrent writes are finite QA bounds. No document promises those response times or a capacity of twenty. IDs, request names, titles, probe strings and count 2 are legitimate fixture choices when their setup is satisfied; they need not appear verbatim in architecture prose.

## Limits and ambiguity register

`AMBIGUITIES.md` resolves A3 against H101-94; revision 14 now has an independent written source. A1's supplied-ID scope is supported by H101-94. A2 remains partial uncertainty coverage; neither this review nor its staging language waives ADR 0004. G1–G7 are not recorded in that file; it was left unchanged.

This traceability ruling does not certify scenario names as coverage. In particular, UI-06's CLI “discover” branch supplies the known task ID despite ADR3:31; several observer/detachment checks call bound sessions directly, which ADR3:50 permits for headless observation but does not establish both adapters' production-path behavior; the detachment helper checks revision/counts rather than all nested values. These limits prevent reading the sourced expectations as proof of the full behavioral contract. Kelly decides their acceptance impact, including missing assertions, after this ruling. No passing-run or Phase 2 item 3 decision is made here.
